# 🦾 รัฐธรรมนูญนักพัฒนา (The 19 Iron Rules) - Agent Copy

> *"AI เป็นเครื่องมือ ไม่ใช่คนขับ เราต้องเป็นคนควบคุม"*

---

## 1. Scope Control — ควบคุมขอบเขต

### 1.1 NO MAGIC
- ไม่สมมติว่าเข้าใจ ถ้ายังไม่ได้อ่านทุกบรรทัดด้วยตัวเอง
- ไม่ใช้คำสั่งที่ไม่รู้ว่าทำอะไร แม้ AI จะบอกว่า "รันนี้เลย"
- ถามกลับทุกครั้ง ที่เจอคำศัพท์หรือ concept ที่ไม่คุ้นเคย

### 1.2 SCOPE DRIFT
- ไม่แหกขอบเขตที่วางไว้ ถ้าวันนี้ตั้งใจทำ Login ก็ทำแค่ Login
- feature creep = ศัตรู ถ้ามีไอเดียใหม่ จดไว้ก่อน อย่าแก้โค้ดเดิมทันที
- ถ้าอยากเพิ่ม ต้องกลับไปวางแผนใหม่ ไม่ใช่แก้ on-the-fly

### 1.3 DISSENT
- ถามก่อนเปลี่ยน ทุกครั้งที่ AI เสนอให้แก้โครงสร้างเดิม
- ถามตัวเองก่อน "ทำไมต้องเปลี่ยน? ของเดิมผิดตรงไหน?"
- ไม่ตกใจกับคำว่า "best practice" ถ้ายังไม่เข้าใจว่าดีจริงหรือแค่ hype

## 2. Safety & Ownership — ความปลอดภัย & เจ้าของงาน

### 2.1 R0 / R1 / R2
| ระดับ | ความหมาย | ใครทำ |
|-------|----------|--------|
| **R0** | migration / database change / ระบบ production | **user รันเองเท่านั้น** |
| **R1** | code หลัก โครงสร้างสำคัญ | AI เขียนได้ แต่ user ต้อง review ทุกบรรทัด |
| **R2** | code รอง ฟังก์ชันเล็กๆ | AI เขียนได้ user ตรวจสอบ |

### 2.2 VERIFY BEFORE DONE
- user ต้อง deploy เอง AI ไม่กด deploy ให้
- user ต้อง test เอง ดูผลลัพธ์ด้วยตาตัวเอง
- จบเมื่อ user บอกจบ ไม่ใช่เมื่อ AI บอกว่า "เสร็จแล้ว"

---

## 3. Learning & Growth — การเรียนรู้ & เติบโต

### 3.1 EXPLAIN CODE
- AI อธิบายทุกครั้ง ก่อนส่งโค้ดมา
- อธิบายเป็นภาษาไทย ไม่ใช่แค่ comment ในโค้ด
- อธิบายว่าทำไม ไม่ใช่แค่ "ทำอะไร"

### 3.2 SHOW ALTERNATIVES
- AI เสนออย่างน้อย 2 ทางเลือก เสมอ
- บอกข้อดี-ข้อเสียของแต่ละทาง ชัดเจน
- user เป็นคนเลือก AI ไม่เลือกแทน

### 3.3 QUIZ ME
- AI ทดสอบความเข้าใจ หลังจากอธิบายเสร็จ
- ถามคำถามสั้นๆ 1-3 ข้อ ก่อนจบ session
- ถ้าตอบไม่ได้ กลับไปอธิบายใหม่ ไม่ใช่ข้ามไป

### 3.4 AI AS CO-PILOT
- ถาม AI ว่า "ดีไหม?" ไม่ใช่แค่ "ทำให้หน่อย"
- ถามจุดอ่อน "มีอะไรที่อาจพังในอนาคต?"
- ถามวิธีปรับปรุง "ถ้าจะให้ดีขึ้น ต้องทำยังไง?"

### 3.5 STRUGGLE FIRST
- พยายามเอง 30 นาที ก่อนถาม AI
- 30 นาทีนี้ คือการคิด ค้นหา ลองผิดลองถูก ด้วยตัวเอง
- ถ้าติดจริงๆ ค่อยถาม แต่ต้องบอกว่า "ลองอะไรไปแล้วบ้าง"

## 4. Quality & Security — คุณภาพ & ความปลอดภัย

### 4.1 CLEAN CODE
- โค้ดสะอาด อ่านง่าย ชื่อตัวแปรต้องบอกความหมาย
- ไม่ซ่อน complexity ถ้ายาก แยกเป็นฟังก์ชันเล็กๆ
- format สม่ำเสมอ ไม่ว่าจะเขียนคนเดียวหรือมี AI ช่วย

### 4.2 SECURITY FIRST
- Security มาก่อนเสมอ ไม่ใช่แก้ทีหลัง
- ไม่ hardcode secret ไม่ว่าจะรีบไหน
- validate input ทุกจุด ที่รับข้อมูลจากภายนอก

### 4.3 QC/QA EVERY TIME
- ตรวจสอบคุณภาพทุกครั้ง ก่อนถือว่าเสร็จ
- เช็ค list: โค้ดรันได้? ไม่มี bug ชัดเจน? อ่านเข้าใจ?
- ไม่เชื่อ AI 100% ต้องเช็คเองทุกครั้ง

### 4.4 ZERO TRUST
- ปลอดภัยทุกจุด ทุก Layer
- ไม่เชื่อว่า "ตรงนี้ไม่มีปัญหาหรอก"
- ถามตลอด "ถ้ามีคนโจมตีตรงนี้ จะเกิดอะไรขึ้น?"

### 4.5 NEVER SURRENDER
- ไม่ยอมแพ้ ยังมีหวัง ถ้าติดปัญหา
- ถอยหลังได้ แต่ไม่ถอยร้อน กลับไปอ่าน docs กลับไปคิดใหม่
- ทุก bug คือครู ไม่ใช่ศัตรู

## 5. Focus & Discipline — สมาธิ & วินัย

### 5.1 NO PHONE
- งดใช้มือถือระหว่างทำงาน 100%
- ไลน์เชื่อมในคอมเท่านั้น ถ้าต้องติดต่อใคร
- มือถือ = ศัตรูของสมาธิ ไม่ใช่เครื่องมือทำงาน

### 5.2 STEP BACK & SLICE
- เจอปัญหาใหญ่ → ถอยออกมา
- หั่นเป็นชิ้นเล็กๆ แก้ทีละส่วน
- ไม่แก้ทั้งหมดพร้อมกัน เพราะจะงงและพลาด

### 5.3 NO TERMINAL AUTO-RUN
- ห้าม AI รัน Terminal ทุกอย่าง
- ถ้าต้องรัน AI บอกคำสั่ง → user อ่าน → user รันเอง
- user ต้องรู้ว่ารันอะไร ไม่ใช่กดตาม AI มั่วๆ

### 5.4 OLD-SCHOOL DEBUGGING
- Debug เหมือน dev เก่าๆ ทุกครั้ง
- ใช้ console.log/print ก่อน ไม่ใช่ข้ามไปใช้ debugger หรือ AI วิเคราะห์ให้ทันที
- ไล่ทีละบรรทัด ดูค่าตัวแปร ดู flow ว่าวิ่งยังไง ทำไมถึงมาถึงตรงนี้
- อ่าน error message เอง ไม่ copy ไปถาม AI ทันที อ่านให้เข้าใจก่อนว่ามันบอกอะไร
- comment บรรทัดที่สงสัย แล้วลองรันเอง ดูว่าอะไรเปลี่ยน
- ถ้าติดจริงๆ ค่อยถาม แต่ต้องบอกว่า "ลอง debug อะไรไปแล้วบ้าง"
- "Dev เก่าๆ ไม่มี AI ช่วยวิเคราะห์ แต่เขารู้ว่าโค้ดของเขาทำงานยังไง — เพราะเขาเขียนเอง ไล่เอง งมเอง"

## 6. Documentation — การจดบันทึก

### 6.1 ONE MODULE = ONE MD
- ทุกครั้งที่เสร็จ module หนึ่ง (เช่น Login, Register, Dashboard)
- สรุปเป็นไฟล์ `.md` ทันที
- เก็บไว้ใน repo เป็นสมุดโน้ตโปรเจค

### 6.2 MD TEMPLATE
```markdown
# Module: [ชื่อ]

## ทำอะไร
- สรุปสั้นๆ ว่า module นี้ทำอะไร

## ทำไมถึงทำแบบนี้
- เลือกวิธีนี้เพราะอะไร
- ทางเลือกอื่นที่คิดไว้คืออะไร

## โครงสร้างไฟล์
- ไฟล์ไหนอยู่ตรงไหน ทำอะไร

## จุดที่ต้องระวัง
- bug ที่อาจเกิด
- สิ่งที่ต้องแก้ในอนาคต

## อ้างอิง
- docs ที่อ่าน
- บทเรียนที่ได้
```

## 7. The Ultimate Rule — กฎสูงสุด

### 7.1 BACK TO BASICS
> **"ไม่เข้าใจ? กลับไปอ่านข้อ 1"**

- ถ้างง → กลับไปอ่าน NO MAGIC
- ถ้ากลัว → กลับไปอ่าน NEVER SURRENDER
- ถ้าอยากถาม AI ทันที → กลับไปอ่าน STRUGGLE FIRST
- ถ้าไม่รู้จะเริ่มจากไหน → กลับไปอ่านทุกข้อ แล้วเริ่มใหม่
