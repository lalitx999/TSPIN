1. ข้อจำกัดทางกฎหมายในประเทศไทย
1.1 กฎหมายหลักที่เกี่ยวข้อง
(1) PDPA (Personal Data Protection Act)
กฎหมายคุ้มครองข้อมูลส่วนบุคคลของไทย
👉 ข้อมูลสุขภาพ = “Sensitive Personal Data”
สิ่งสำคัญมาก
คุณ “ห้ามเก็บ ใช้ เปิดเผย” เว้นแต่มี
consent ชัดเจน
หรือเข้าข้อยกเว้นเฉพาะทาง (ซึ่งใช้ยากในธุรกิจ)
1.2 ข้อมูลสุขภาพ = ข้อมูลอ่อนไหวสูงสุด
ตัวอย่างข้อมูลที่ TSPI จะเก็บ เช่น
ประวัติการรักษา
ผลเลือด
microbiome
genomics
ยาที่ใช้
lifestyle
wearable data
ทั้งหมดนี้ = sensitive data
1.3 หลักการสำคัญของ PDPA ที่ TSPI ต้องปฏิบัติ
1. Purpose limitation
ต้องระบุว่าเก็บเพื่ออะไร
👉 ห้ามใช้ “เผื่อไว้ก่อน”
2. Data minimization
เก็บเท่าที่จำเป็น
3. Consent ต้องชัด
ต้องเป็น “explicit consent”
แยกเป็นแต่ละวัตถุประสงค์
4. Right ของเจ้าของข้อมูล
ผู้ใช้ต้องสามารถ
ขอข้อมูล
แก้ไข
ลบ
ถอน consent
5. Security
ต้องมีมาตรการ
encryption
access control
audit log
1.4 ข้อจำกัดสำคัญสำหรับ TSPI
❌ คุณไม่สามารถ

❌ ห้ามใช้ข้อมูลไปทำวิจัย

❌ ห้าม cross-border data flow
ถ้าประเทศปลายทางไม่มีมาตรฐานเพียงพอ (ต้องระวังถ้า TSPI เป็น global)
2. ความเสี่ยงสำคัญของ TSPI ในประเทศไทย

👉 “เก็บข้อมูลมากเกินไปโดย consent ไม่ชัด”
2.2 ความเสี่ยงรอง
1. โรงพยาบาลไม่เชื่อม
เพราะ:
กลัวผิด PDPA
กลัว data leakage
2. คนไข้ไม่กล้าใช้
ถ้ารู้สึกว่า:
ข้อมูลถูกเอาไปใช้โดยไม่รู้ตัว
3. งานวิจัยใช้ไม่ได้
ถ้า consent ไม่ถูกต้องตั้งแต่แรก
3. วิธีออกแบบ Consent สำหรับ TSPI (สำคัญที่สุด)
นี่คือหัวใจของระบบคุณ

Part 2: HIPAA-ready / PDPA-ready Data Architecture
This architecture should be designed to support:
role-based access

auditability
identity verification
secure transmission

consent-driven sharing
These align with key HIPAA Privacy and Security Rule expectations around access control, audit controls, authentication, integrity, transmission security, minimum necessary use, and user access rights. �

A. Architecture principles
Patient-controlled by default
Zero implicit sharing
Consent is a first-class data object
Everything is logged
Access is role-based and purpose-bound
Interoperability through APIs, preferably FHIR-aligned
Separation of identity, clinical data, and analytics
Encryption in transit and at rest

consent withdrawal

cross-border transfer control rules

Security Principles ที่ควรใช้
1. Zero Trust

แนะนำ

Expiry Logic
ลิงก์ควรหมดอายุด้วย 3 แบบพร้อมกัน
A. Time Expiry
เช่น 7 วัน
B. Max View Expiry
เช่น เปิดได้ไม่เกิน 10 ครั้ง
C. Session Idle Timeout
ถ้า doctor ไม่ active 15 นาที ให้ออกจากระบบ
Revoke Logic
เมื่อ revoke:
update status = revoked
set revoked_at
invalidate all view sessions for share_id
log event share_revoked
doctor access page แสดง “This access has expired or been revoked”
OTP Logic
แนะนำ 2 แบบ
OTP ส่งไปยังเบอร์หรืออีเมลที่ผู้ป่วยกำหนดสำหรับแพทย์
หรือ patient-defined PIN แชร์แยกทางโทรศัพท์/LINE
ถ้าต้องการ friction ต่ำ:
default = secure link + PIN
higher security = secure link + OTP

A. Integrated Health Summary
โครงสร้างที่แนะนำ
หัวข้อหลัก
ภาพรวมสุขภาพของคุณวันนี้
สรุปสั้น
จากข้อมูลสุขภาพที่มีอยู่ ระบบพบแนวโน้มที่ควรติดตาม 3 เรื่อง ได้แก่ ระดับน้ำตาลที่สูงขึ้นต่อเนื่อง ความเสี่ยงด้านไขมันในเลือด และความเหมาะสมของยาบางชนิดกับข้อมูลสุขภาพของคุณ
สิ่งสำคัญที่พบ
ระดับน้ำตาลในเลือดมีแนวโน้มสูงขึ้นต่อเนื่อง
มีความเสี่ยงด้านหัวใจและหลอดเลือดเพิ่มขึ้นจากหลายข้อมูลร่วมกัน
ยาบางชนิดควรตรวจสอบความเหมาะสมเพิ่มเติมจากข้อมูลพันธุกรรมและประวัติการใช้ยา
สิ่งที่ควรทำต่อ
นำรายงานนี้ให้แพทย์ดู
ติดตามผลเลือดครั้งถัดไป
ตรวจสอบรายการยาที่ใช้อยู่
อัปโหลดผลตรวจล่าสุดเพิ่มเพื่อให้ระบบวิเคราะห์ละเอียดขึ้น
หมายเหตุ ข้อมูลนี้เป็นการวิเคราะห์เบื้องต้นจากข้อมูลที่คุณอนุญาตให้ระบบใช้

Role: You are a clinical summarization assistant for MiHealth AI.

Licensed physician / clinical staff.

Professional, concise, clinically useful.
